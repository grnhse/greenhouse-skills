# Candidate status

Resolve the candidate → one parallel read batch → duplicate sweep and names → compute → render → Next. Budget: 4-5 calls in QUICK mode (search, candidate, reqs, stages, plus reasons when a row is closed), 7-8 in FULL, up to 11 with the duplicate sweep; 11-12 with every enhancement. No Greenhouse writes; this skill never summarizes interview feedback.

## Needs

| Tool | Role | Without it |
|---|---|---|
| `whoami` | optional: who is asking, with no email question | a profile line, a stated user id, or the login email |
| `search_applications` | core: resolve a name or email to a candidate and every application | stop; point to /greenhouse:configure (needs harvest:applications:list) |
| `list_candidates` | core: header fields and flags; the match check; the email fallback | header shows the name as typed |
| `list_applications` | core: applications after the email fallback or a full search page | rows from the search only |
| `search_candidates` | core: the duplicate sweep in full mode | "Duplicates: not checked" |
| `list_jobs` | core: req names, status, `confidential` | req cells read "req not visible"; never print a job id |
| `list_job_stages` | core: stage k of n | stage name alone |
| `list_scorecards` | core: scorecards in, started but not submitted | scorecard cells read "not visible" |
| `list_rejection_reasons` | core: withdrew versus not moving forward, reason name | "Closed <date>, reason not visible" |
| `list_users` | core: recruiter, coordinator, interviewer names | "name not visible to your account"; keep the counts |
| `list_interviews` | enhancement: next interview per application | the Next ladder starts at drafts |
| `list_offers` | enhancement: current offer per application | "Offer: not visible" |
| `list_application_stages` | enhancement: exact days in the current stage | "no activity recorded for N days" instead |
| `list_notes` | enhancement: last logged email | line omitted |

## Steps

1. **Parse the ask (no calls).** `QUERY` = the name or email exactly as given; `JOB_HINT` when a req is named; `NOW`. Mode: a one-line ask ("where is", "still active?", "is she in process") is QUICK; an open-ended ask ("tell me about", "history", "have we talked to", "pull up") is FULL. `ME` = the user id from a "Greenhouse profile: ... user_id=" line the user has given you, in this conversation or in the instructions they wrote for you, else `whoami` when it is listed (with step 2's call), else unknown; never ask for the email here.

2. **Resolve (1 call).** `search_applications(search: QUERY, job_status: "all", per_page: 20, fields: ["id", "candidate_id", "job_id", "status", "stage_name", "job_interview_stage_id", "prospect", "prospective_job_ids", "recruiter_id", "coordinator_id", "referrer_id", "needs_decision", "rejection_reason_id", "last_activity_at", "rejected_at", "created_at"])`. Always pass `job_status: "all"`: without it the search covers open reqs only, and history questions are about closed ones. Group rows by `candidate_id`.
   - One candidate: `CID` = that id, `APPS` = all of their rows, every status. The index allows near matches: after step 3 loads the profile, if neither the name nor one of its `email_addresses` matches `QUERY`, show the match and ask before rendering.
   - Several candidates: in one batch `list_candidates(ids: <the candidate ids, at most 50>, fields: CANDIDATE_FIELDS)` and `list_jobs(ids: <their non-null job ids, at most 50>, fields: ["id", "name", "status", "confidential"])`. List up to 10 as "<full name>, <title> at <company>: <req> (<stage>, <status>)" and ask which, as a numbered list. Never guess, even when one looks likelier; more than 10: ask for the full name or an email. On the pick, reuse both lookups. When the search returned a full page of 20, the pick's rows may be incomplete: `list_applications(candidate_ids: [CID], per_page: 50, fields: [as in the search])` replaces `APPS` (+1 call).
   - Empty and `QUERY` contains "@": `list_candidates(email: QUERY, fields: CANDIDATE_FIELDS)`. Found: `CID` = its id, then `list_applications(candidate_ids: [CID], per_page: 50, fields: [as in the search])` = `APPS`; an empty `APPS` means "profile exists, but no application is visible to you".
   - Empty otherwise, or the fallback found nothing: say "No candidate matching <QUERY> is visible to you. Private candidates and other teams' reqs can be hidden; try the full name or an email address." Stop. Never widen the search or pick a near match.

3. **Parallel batch (3-4 calls in QUICK, 4-5 in FULL).** Skip any call whose id list is empty: no job (prospect only) skips `list_jobs` and `list_job_stages`; no application skips `list_scorecards` and every application-scoped enhancement read, and the table is the header plus one empty-state sentence. `APP_IDS` = ids in `APPS`; `JOB_IDS` = distinct non-null `job_id` plus every `prospective_job_ids` entry (each at most 50). Skip lookups already loaded in step 2. `CANDIDATE_FIELDS` = `["id", "first_name", "last_name", "preferred_name", "company", "title", "tags", "can_email", "private", "email_addresses", "linked_user_ids", "last_activity_at"]`.
   - `list_candidates(ids: [CID], fields: CANDIDATE_FIELDS)`
   - `list_jobs(ids: JOB_IDS, fields: ["id", "name", "status", "confidential"])`
   - `list_job_stages(job_ids: JOB_IDS, per_page: 100, fields: ["id", "job_id", "name", "sort_order", "active"])`; no `active` filter, so a retired stage still resolves.
   - FULL only: `list_scorecards(application_ids: APP_IDS, per_page: 100, fields: ["id", "application_id", "interviewer_id", "submitter_id", "status", "interviewed_at", "submitted_at"])`; never request `candidate_rating` or the notes fields.
   - Only when a `rejected` row exists: `list_rejection_reasons(include_defaults: true, per_page: 500, fields: ["id", "name", "type"])`.
   - FULL: enhancement reads join this batch (table below).

4. **Duplicate sweep and names (FULL only, one batch of 2-4 calls).**
   - Sweep: `search_candidates(search: "<first_name> <last_name>", job_status: "all", per_page: 20, fields: ["id", "first_name", "last_name", "company", "title", "email_addresses"])`, plus `list_candidates(email: <address>, fields: CANDIDATE_FIELDS)` for at most two addresses on the profile other than the one `QUERY` matched. Rows whose id is not `CID` are possible duplicates, matched on "same email address" or "same name"; a third or later address is "not checked".
   - Names: `PEOPLE` = distinct `recruiter_id`, `coordinator_id` from `APPS`, `interviewer_id`, `submitter_id` from the scorecards, `user_id` from notes (at most 50; skip the call when empty). `list_users(ids: PEOPLE, fields: ["id", "first_name", "last_name", "name", "deactivated"])`. Empty or denied: names not visible to this account; keep every count.

5. **Compute (no calls).** Per application in `APPS`:
   - Status: `in_process` → Active. `hired` → Hired (its stage is null; it reached the last stage). `converted` → Converted from prospect. `rejected` → by the reason's `type.key`, compared ignoring case: `they_rejected_us` → "Withdrew <date>"; any other → "Not moving forward <date>, reason as recorded: <name>" or "no reason recorded" (quoted as data, never adopted as wording); a `security_concern` type → show the recorded reason, add nothing else, and point to the recruiter on that application. `prospect: true` → Status "Prospect", req cell the prospective req names (or "no job yet"), no stage, never counted as active.
   - Stage: `stage_name` plus "(k of n)", where the req's active stages are ordered by `sort_order`, n is their count and k the position of `job_interview_stage_id`; omit "(k of n)" for a retired stage, a hired row or a prospect. k of n says how far the process went, not how well.
   - Since: "no activity recorded for N days" from `last_activity_at`, which is per candidate, so every row of one person shows the same number; say "last recorded activity on this candidate" once. Null → count from `created_at` and write "since they applied". Under 24 hours: "last recorded activity today" or "yesterday", by calendar date.
   - Scorecards (FULL): "k in" = `status: "complete"`; "m started but not submitted" = drafts, each named with "scorecard dated <interviewed_at>". A draft on an active row is owed when `interviewed_at` has passed and is within 30 days: "from <interviewer>, scorecard dated <date>" ("yours" when `interviewer_id` is `ME`); older → "stale draft from <date>"; future or missing date → "not yet due"; on a closed row it reads "draft, never submitted". Never show ratings here (candidate-debrief's job). Say once that an interview with no scorecard row is not visible without `list_interviews`.
   - Next, per active row, first that applies: next interview (enhancement) · a draft owed ("from <interviewer>, scorecard dated <date>"; "yours") · `needs_decision` → "A decision is waiting on this application; Greenhouse doesn't say whose" · stage named Offer → "In Offer" plus the offer line when visible · every scorecard complete and none dated ahead → "All k scorecards are in, the last n days ago" · no activity recorded for 14 or more days → "ask <recruiter>" or "you are the recruiter on it" · else "Nothing is flagged; last recorded activity n days ago."
   - Ask, per application: "<recruiter> (recruiter) and <coordinator> (coordinator), <span>" with the span as "Sep 2026 to now" (from `created_at` to `rejected_at`, "to hire", or "now"); then interviewers whose scorecard date has passed, each "submitted" or "draft", never the rating. A blank recruiter or coordinator reads "Nobody recorded" and sorts first; deactivated users last with "no longer active in Greenhouse". When `ME` is the recruiter or coordinator, write "You are the recruiter on <req>" (or coordinator) instead of listing them.
   - Header flags: "Internal candidate" when `linked_user_ids` is not empty; "Referral on record" when `referrer_id` is set (no name); "Private candidate: don't forward" when `private`; "can't be emailed (opted out)" when `can_email` is false. A blank or hidden name shows what came back, never worked out from other fields.
   - Turning points, from dates only: first applied (month and req) · each outcome with its date · "applied again <n> days after <req> closed" when a later `created_at` follows a `rejected_at` · "no activity recorded for n days" on an active row at 14 or more. A quiet stretch is a gap in our record, never a remark on the person's career.
   - Duplicates: each possible duplicate prints "Could be the same person: <name>, <title> at <company>, same email address · [profile]" (or "same name"; never the address); their history stays out of every count; never say whether it is the same person. Capped addresses add "n more addresses not checked".
   - Headline, one sentence shaped by the ask. Where-is, one active row: "<Name> is in <stage> for <req>, stage k of n" (drop it when omitted); several: "<Name> is active on <n> reqs: <stage> for <req> and <stage> for <req>". No active row, from the latest closed one: "<Name> isn't in process: not moving forward at <stage> for <req> on <date>" or "<Name> isn't in process: withdrew from <req> on <date>"; hired: "<Name> was hired for <req>"; prospect only: "<Name> is a prospect, not yet on a req". History: "Yes: <Name> interviewed for <req> in <Mon YYYY> and is now in <stage> for <req>" or "Yes: <Name> applied to <req> in <Mon YYYY>, with no interview that you can see"; "interviewed" only when a visible scorecard's `interviewed_at` has passed, an application alone is "applied".
   - Order: Active rows by newest `created_at`, then Hired, Converted, Withdrew and Not moving forward by date (within the closed rows, one with no reason or no date recorded sorts first), prospects last. With `JOB_HINT`, lead with that req's row and summarize the others in one line. This skill reports workflow facts only, so it makes no AI opt-out check.

6. **Render.** QUICK: the headline, the scope line and "(k earlier applications. Want the full status?)" with k = rows not in the headline ("(No other applications that you can see.)" at zero), then Next. FULL: the whole Output.

## Output

## Edge cases

- **Two people with the same name:** list up to 10 with title and company and ask; never guess or print an address to tell them apart.
- **Private candidate:** `private` true adds "Private candidate: don't forward" to the header; the rest renders as usual.
- **Prospect with no job:** Status "Prospect", req cell "no job yet", no stage or k of n, Next reads "Prospect: not in a process", counted in no total.
- **Hired:** null stage, so the Stage cell reads "Hired (reached the last stage)" with no k of n and no Next line; the Ask span ends "to hire".
- **Email given instead of a name:** search first, then the email fallback; the header shows the name Greenhouse returned, and the address is never echoed back.
