# Interview week

Budget: 7 calls on the default tools, where the calendar itself is not visible; 13-15 with every enhancement, hard cap 18. Over the cap, cut the all-day read, then the second interviewer batch, and say what was cut. No Greenhouse writes.

## Needs

| Tool | Role | Without it |
|---|---|---|
| `whoami` | optional: who is asking, with no email question | a profile line, a stated user id, or the login email |
| `list_users` | core: identity from email; interviewer and coordinator names | ask which reqs to show; "an interviewer", "the coordinator" |
| `search_jobs` | core: open reqs where the user is recruiter or coordinator, or the req they name | the skill cannot run; point to `/greenhouse:configure` |
| `list_applications` | core: the active application behind each interview: candidate, stage, coordinator | the skill cannot run; say so |
| `list_scorecards` | core: scorecards in or started, by status and date only | Awaiting feedback lists interviews, not interviewers; no nudges |
| `list_candidates` | core: names for printed rows | "Candidate <link>" in place of a name |
| `list_interviews` | enhancement: the calendar, what is still to schedule, interviews awaiting feedback (below) | "interview times: not visible"; feedback from started scorecards only |
| `list_interviewers` | enhancement: each panel, calendar replies, scorecard ids (below) | "panel: not visible"; feedback owed only where a scorecard was started |
| `list_job_interviews` | enhancement: the interview's name and planned length (below) | "interview in <stage>" from the application's current stage |
| a connected chat or email tool | sends an approved nudge | nudges are printed to copy |

## Steps

Logistics only: no candidate summaries or comparisons, so the AI opt-out check does not apply. Never request `candidate_rating`, a notes field, the `email` field of `list_interviewers`, `video_conferencing_url` or `location`: rooms and links stay in Greenhouse.

1. **Inventory and window (no calls).** In this first turn also read `page/PAGE.md`, alongside step 2 or 3's first call. Note which tools above are listed (when tools load on demand through a tool search, load all eight first with one search naming each exactly as your tool list shows it, prefix included). None listed: rule 0 and stop. Set NOW; TODAY = the user's local date (zone from a "Greenhouse profile" line the user shared or from the conversation, else UTC, and say so). `WINDOW` = start of TODAY to the start of the day 7 days later, also for "this week"; a named day ("tomorrow", "Friday") is that local day; "next week" and "last week" run Monday to Sunday; a named range at most 31 days. A past window shows what happened and what is still owed. Send both bounds as UTC date-times.

2. **Identity (0 or 1 call).** A named req ("the designer req") needs no identity: go to 3b. Otherwise `ME` comes from a "Greenhouse profile: ... user_id=" line the user has given you (in this conversation or in the instructions they wrote for you), else from `whoami` when it is listed, else from the login email they gave you the same way; else ask once: "Which email do you sign in to Greenhouse with?" Then `list_users(primary_email: <email, lowercased>, fields: ["id", "first_name", "name"])`.
   - One user: `ME` = id, `FIRST` = first name. A revoked-token text here is rule 4: stop.
   - Empty: "No Greenhouse user I can see has <email> as its primary email. Try another address, or name the reqs you want." One retry, then 3b; never widen to the whole organization.
   - Denied or `list_users` absent: run from job names (3b) and say names will not resolve.

3. **Your reqs (one parallel batch, 2 calls).** `search_jobs(user_id: ME, user_role: "recruiter", status: "open", per_page: 100, fields: ["id", "name", "confidential", "requisition_id"])` and the same with `user_role: "coordinator"`. Union by id = `JOBS`.
   - 3b, named reqs: per name (with a job id too: keep the row whose `id` matches, following the cursor once; a job id alone: ask for the name), `search_jobs(search: <name>, status: "open", per_page: 5, fields: as above)`; several matches: show name and req id, ask which; none: re-issue once with `status: "all"` and say when the match is closed or a draft.
   - Empty: "You're not recruiter or coordinator on any open job that I can see. Name the reqs you want and I'll run on those." Stop; no other job read. More than 50 jobs: say how many and ask which to show first.

4. **Desk reads (one parallel batch, scoped to `JOBS`; the enhancement reads join it, see below).**
   - `list_applications(job_ids: JOBS, status: "active", prospect: false, per_page: 500, fields: ["id", "candidate_id", "job_id", "stage_name", "job_interview_stage_id", "coordinator_id", "recruiter_id"])` = `APPS`. Page with `cursor` alone, at most three pages; a full third page: "at least" on every total. A denied, rate-limited or errored call in this batch follows its rule for its section only.
   - Only when `list_interviews` is absent: `list_scorecards(status: "draft", interviewed_at: {gte: <NOW minus 30 days>, lte: <NOW>}, per_page: 500, fields: ["id", "application_id", "interviewer_id", "interviewed_at", "status"])`, kept where `application_id` is in `APPS` = `DRAFTS`. Then skip to step 6.

5. **Panels and scorecards (one parallel batch, after step 4; only with `list_interviews`).** `SHOWN` = `WEEK`, `ALLDAY` and `AWAITING` (below), soonest first, at most 100; count the rest.
   - `list_interviewers`, when listed: see "With more tools switched on" = `PANEL`.
   - `list_scorecards(application_ids: <application ids on AWAITING, at most 50>, per_page: 500, fields: ["id", "application_id", "interviewer_id", "status", "interviewed_at", "submitted_at"])` = `CARDS`; skip when `AWAITING` is empty; beyond 50 ids one more call, then "feedback: not checked".
   - Interviews in `SHOWN` whose `application_id` is not in `APPS`: `list_applications(ids: <those ids, at most 50>, per_page: 50, fields: ["id", "candidate_id", "job_id", "stage_name", "status"])` = `CLOSED`; skip when there are none. An id in neither list: keep the row as "Candidate not visible", no link.

6. **Names (one parallel batch, after the rows are picked).**
   - `list_candidates(ids: <up to 50 candidate ids on printed rows>, per_page: 50, fields: ["id", "first_name", "last_name", "preferred_name"])`; one more call beyond 50, the rest by link.
   - `list_users(ids: <up to 50 user ids>, per_page: 50, fields: ["id", "first_name", "last_name", "name"])`: interviewers owing feedback first, then interviewers on `WEEK`, coordinators, organizers; one more call beyond 50, then "an interviewer". Never `primary_email` here.

7. **Compute the sections (no calls).** Display name = `preferred_name`, else first and last name. Times are local to the user, 24-hour, "Fri 16 Oct, 10:00–11:00". Interview name = the slot's `name`, else "interview in <stage_name>". Earliest first everywhere; never order people by anything but time.
   - **This week**: one row per `WEEK` and `ALLDAY` interview: day, time ("All day" for `ALLDAY`), candidate, req, interview, panel, status. Status from `status`: `scheduled` → Scheduled; `awaiting_feedback` → Scorecard due; `complete` → Feedback in; `skipped` → Skipped; `sent` and `received` (take-home tests) → Test sent, Test received. Panel = interviewer names in `PANEL` order, a row with no `user_id` as "an external interviewer"; replies as counts under it from `response_status` ("1 declined · 1 not replied · 1 tentative"; `needs_action` is not replied). A `scheduled` interview with a declined interviewer, or with no interviewer rows at all, reads Panel change needed. An application in `CLOSED`: Application closed, with "the application is <rejected or hired>; the calendar invite may still be live".
   - **Still to schedule**: `TO_SCHEDULE` rows whose application is in `APPS`, kept only where the slot's `job_interview_stage_id` equals the application's `job_interview_stage_id` (a slot opens per interview when a candidate enters a stage, and slots from passed stages can stay open); without `SLOTS` keep them all and say "may include interviews from stages already passed". One row per application: slot names, how many, days waiting = whole days from the oldest slot's `created_at` to NOW ("since the slot opened", never "overdue"), "availability in since <date>" when a slot has `availability_received_at`, the coordinator. Longest waiting first, at most 25 rows, then "and N more".
   - **Awaiting feedback**: per `AWAITING` interview and per `PANEL` interviewer with a `user_id`: submitted = `CARDS` has a `complete` row whose `id` is the interviewer's `scorecard_id`, or, when that is null, one with the same `application_id` and `interviewer_id` and an `interviewed_at` on the interview's day; "started, not submitted" = such a row in `draft`; else "not started". Submitted interviewers are left out. Group by interviewer, oldest interview first (never by count), with hours since the interview ended (never "overdue"). Without `PANEL`: the interviewers holding a `draft` in `CARDS`, plus each other `AWAITING` interview once as "feedback outstanding (interviewers not visible)", a lower bound. Without `list_interviews`: `DRAFTS` by interviewer, titled "Scorecards started but not submitted", with the access line "Interviewers who haven't opened their scorecard show up only with interview access (harvest:interviews:list)." The user's own row reads "You:", no nudge, with `/greenhouse:scorecard-draft` as its step. Counts only: never a rating, never scorecard text.
   - **By interviewer**, only when asked ("who's interviewing tomorrow"): interviewers in `WEEK` with their interviews in time order. A count describes their calendar that week, nothing else.
   - **Headline**, first that holds, with the window in words ("in the next 7 days", "tomorrow", "next week"): (a) `list_interviews` absent: "I can't see interview times with your current access; n scorecards from the last 30 days are started and not submitted"; (b) any `WEEK` or `ALLDAY` row: "N interviews are on the calendar <window> across your R open reqs, k of them today" (drop the last clause when TODAY is outside the window or k is 0; one named req: "on <req>"); (c) none, To schedule not empty: "No interviews are on the calendar <window>; n candidates are waiting for one to be scheduled"; (d) none, feedback owed: "No interviews are on the calendar <window>; n scorecards are still owed from earlier interviews"; (e) "No interviews are on the calendar <window>, nothing is waiting to be scheduled and no feedback is owed, that you can see." Match the verb to the count. An empty week still gets what is to schedule and owed; never guess at interviews from stage names.

8. **Render and close.** Per Output. End with the rule 1 footnote naming the sections not visible and their scope keys (interview times, still to schedule, interviews awaiting feedback: harvest:interviews:list; panels, replies, scorecards not started: harvest:interviewers:list; interview names: harvest:job_interviews:list), then the Next prompts. Asked to schedule, move or cancel an interview or email a candidate: "I can't change the calendar from here; that happens in Greenhouse." with the application link. Posting somewhere shared: counts and times only, no candidate names, exact text and destination shown, one send on an explicit yes.

9. **Nudges (outside Greenhouse).** One per interviewer owing feedback, two lines: "Hi <first>, Greenhouse is still waiting on your scorecard for <candidate> (<req>, <interview>, <Tue 13 Oct>)." and "The team needs it to decide; if the interview moved or you weren't on it, let me know. Thanks, <user first name>" (several candidates: name each in line one, "scorecards", "them"; no sign-off name when `FIRST` is unknown). A private candidate reads "a candidate" with the application link. Never ratings, notes or contact details. On the page they are copy buttons; in chat, print them when asked. With a connected chat or email tool, resolve addresses only now with `list_users(ids: <interviewers to nudge>, per_page: 50, fields: ["id", "primary_email"])`, never print them, and send one message per explicit yes ("Reply yes to send this to <interviewer name>."), to that person, never a channel.

## Edge cases

- **Feedback collected without a calendar time** (`collect_feedback`, such as an application review): not an interview here; `/greenhouse:daily-brief` covers those scorecards.
