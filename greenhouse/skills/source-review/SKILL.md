# Source review

Budget: 6-8 calls on the default tools, 8-14 with both enhancements; paging adds at most two calls per application list. No Greenhouse writes.

## Needs

| Tool | Role | Without it |
|---|---|---|
| `whoami` | optional: who is asking, with no email question | a profile line, a stated user id, or the login email |
| `search_jobs`, `get_job` | core: resolve the req, or the open reqs where the user is recruiter or coordinator | `get_job` alone: ask for the job id; neither: stop |
| `list_users` | core: identity, only when no req is named | ask which req to review; a named req needs no identity |
| `list_job_stages` | core: plan order; which stage is review, first interview and final | active counts by `stage_name`; the two reached columns read "not computed" |
| `list_applications` | core: every application created in the window, with `source_id` and `referrer_id` | stop: "needs harvest:applications:list; see /greenhouse:configure" |
| `list_rejection_reasons` | core: who ended it, from the reason's `type` | ended as a total; "who ended it: not visible" |
| `list_sources` | enhancement: source names and types | no per-source rows: the totals, the referrer line, "No source recorded" and "n applications across k recorded sources, names not visible"; never print source ids |
| `list_application_stages` | enhancement: "Reached" from stage history | "Reached at least (derived)" from where each application stands or ended |

## Steps

This skill describes sources, never people. No candidate is named, summarized or compared, so the AI opt-out check does not apply; `/greenhouse:candidate-debrief` runs it. Never request `candidate_id`; a referrer is counted, never looked up or named.

1. **Scope and window** (1-3 calls). In this first turn also read `page/PAGE.md`. Set `NOW` (UTC). `WINDOW` = 90 days, or the user's ("last 30 days", "this quarter"; "since it opened" = from the req's `opened_at`); `SINCE` = `NOW` minus `WINDOW`. The window is by `created_at` and is stated in the scope line with its dates; in a sentence it reads "in the last 90 days" or "since it opened on <date>".
   - A req is named: `search_jobs(search: <name>, status: "open", per_page: 10, fields: ["id", "name", "status", "requisition_id", "opened_at", "closed_at", "confidential", "is_template"])`. One row → `JOBS`. Several → show name, req id and opened date, ask which; never guess. None → re-issue once with `status: "all"`; a closed or draft match is reviewable, say so. Still none → "No job I can see matches <name>; private jobs and other teams' jobs may be hidden." and stop. Given an id: `get_job(job_id: <id>)`; `[]` → "not found or not visible to you", stop. `is_template` true: no applications, stop.
   - No req is named: `ME` = the user id from a "Greenhouse profile: ... user_id=" line the user has given you (in this conversation or in the instructions they wrote for you); else `whoami` when it is listed; else their login email given the same way → `list_users(primary_email: <email, lowercased>, fields: ["id", "first_name"])`; else ask once: "Which req, or which email do you sign in to Greenhouse with?" Empty or denied: ask for a req name; never widen to the whole organization. Then, in one batch, `search_jobs(user_id: ME, user_role: "recruiter", status: "open", per_page: 100, fields: <as above>)` and the same with `user_role: "coordinator"`; union by id = `JOBS`. Empty: "You're not recruiter or coordinator on any open job that I can see. Name the req you want reviewed." and stop. More than 50: say how many and ask which reqs or department first.

2. **Plan and applications** (one parallel batch, 4 calls).
   - `list_job_stages(job_ids: JOBS, active: true, per_page: 500, fields: ["id", "job_id", "name", "sort_order"])` → per req, `STAGES` by `sort_order`. Same roles as pipeline-review: `REVIEW` = the stage named Application Review, else the first; `FIRST_INTERVIEW` = the first later stage with Screen, Interview, Onsite or Panel in its name and without Pre-Screen, Assessment or Test, else the next; `FINAL` = the last stage with neither Offer nor Reference in its name; `LATE` = the last three.
   - `list_applications(job_ids: JOBS, status: "active", prospect: false, created_at: {gte: SINCE}, per_page: 500, fields: ["id", "job_id", "job_interview_stage_id", "stage_name", "created_at", "source_id", "referrer_id"])` → `ACTIVE`.
   - The same with `status: "rejected"` and two more fields, `"rejected_at"` and `"rejection_reason_id"` → `ENDED`.
   - The same as the first with `status: "hired"` → `HIRED` (a hired row has a null stage: it reached every stage).
   - `APPS` = the three lists, N = its size. Paging: follow a `cursor` alone, at most two more pages per list (1,500 rows); a list still full after that: "at least" on every total and the scope line, and offer a shorter window or one req.
   - N = 0: the empty state in step 5; make no further call.

3. **Names** (one parallel batch, 0-1 calls; the enhancement reads below join it).
   - `list_rejection_reasons(include_defaults: true, per_page: 500, fields: ["id", "name", "type"])`, only when `ENDED` is not empty. Who ended it comes from `type.key` (ignore case): `we_rejected_them` → "we declined", `they_rejected_us` → "withdrew", anything else or a blank `rejection_reason_id` → "other or none recorded". Reason names are not printed here; `/greenhouse:pipeline-review` lists them.

4. **Compute (no calls).** Everything is a count of applications, not people; one person on two reqs counts twice, and the page says so.
   - **Source rows**: group `APPS` by `source_id`. A null `source_id` is the row "No source recorded": it sorts first and is flagged as a finding. Then the other sources by applications, most first, ties by name; this is order by volume, never a ranking, and no row is called best, worst, strong or weak. More than 29 sources: the rest share one row, "Other sources (k sources)". The row's type is `type.name` as Greenhouse returns it.
   - **Per row**: Applications (created in the window); Active now, with where they stand by stage in plan order; Reached first interview = applications whose last known stage is `FIRST_INTERVIEW` or later (active: the current stage; ended: the stage it ended from; hired: every stage); Reached final stage = the same for `FINAL`; Hired; Ended, split "we declined n · withdrew n · other or none recorded n", with the stage most of them ended from. On default tools both reached columns are labelled "(derived)". An application standing in, or ended from, a stage that is no longer on the plan is counted everywhere except the reached columns; say how many.
   - **Several reqs**: one row per source summed across `JOBS`, each application placed by its own req's roles; "where they stand" uses three groups in place of stage names: Before first interview, Interviewing (`FIRST_INTERVIEW` up to `FINAL`), Final stage or later; each row's detail lists its reqs with their counts, most first, at most ten.
   - **Rates**: a percentage only where ten or more applications stand behind it ("8 of 11 reached Recruiter Screen (73%)"); below ten, the counts alone. Never set one source's rate against another's in words: print both and let the reader compare.
   - **Referrals**, their own line: R = applications with a `referrer_id`, then the same counts as a row (active, reached first interview, reached final stage, hired, ended). Say what it is: "Greenhouse's 'who gets credit' field; it can also hold an agency recruiter or the colleague who added the candidate, and these applications are also counted under their source." With source names visible, add how many of the R sit under a source whose name or type contains "Referral". Never a name, an id or a count per referrer.
   - **Nobody past review**: sources with one or more applications and none that reached `FIRST_INTERVIEW`, as "<Source>: n applications, none reached <first interview stage>: k still active before it, m ended before it"; then one count line.
   - **Behind the late stages**: the active applications standing in `LATE` now, counted by source: "<late stage names> hold n active applications: <Source> a, <Source> b, ...". None: "Nobody is in <late stage names> from this window."
   - **Fresh applications**: F = applications created in the last 14 days; state it wherever reached counts are read: "F of the N were created in the last 14 days and have had little time to move." (F is 0: leave it out.)
   - **Questions for the sourcing sync**: the first four that apply, in this order, each built from the numbers above and nothing else; fewer apply, print fewer; never pad. (a) "n applications have no source recorded: can the source be filled in, and how are they being added?" (b) the largest source with five or more applications and none at `FINAL` or later: "<Source> brought n applications; k reached <first interview stage> and none reached <final stage>: what would we change about where or how the req is posted there?" (c) the source with the most active applications in `LATE` (tie: the one with fewer applications in the window): "<Source> brought n of the N applications and a of the b now active in <late stage names>: is there room to do more there?" (d) three or more withdrawals: "w of the e ended applications withdrew, k of them from <Source>: what did they tell us on the way out?" (e) one source with three quarters or more of N: "<Source> brought n of the N applications: what happens to the req if it slows?" (f) N is ten or more and R is zero: "No application in this window carries a referrer: has the team been asked for referrals on <req>?" (g), only when fewer than two of the others apply: "N applications in <WINDOW> and k reached <first interview stage>: is the thing to work on how many apply, or the first step?"
   - **Headline**, first that holds: the ask names one source or referrals → that row as a sentence ("Job board brought 8 of the 30 applications on <req> in the last 90 days; 2 reached Recruiter Screen and none reached Onsite", "6 of the 30 applications ... carry a referrer"); sources not visible → "N applications were created on <req> in the last 90 days and k reached <first interview stage>; source names are not visible with your access"; one source has half or more of N → "<Source> brought n of the N applications on <req> in the last 90 days", with "(p%)" only when N is 10 or more; else "N applications on <req> in the last 90 days came from k sources; <Source> brought the most, n" (blank sources: "... from k sources, m with no source recorded; ...", k counting recorded sources only). Several reqs: "your n open reqs" in place of the req name.

5. **Render** per Output. N = 0: "No applications were created on <req> in the last <WINDOW> that you can see: none exist, the req is not visible to you, or the window is too short. Tell me a longer window and I'll redo it." A rule 1 footnote names what was hidden: source names (harvest:sources:list), reached from stage history (harvest:application_stages:list).

## Edge cases

- **"Is the job board worth it?"**: give its row and its share of the applications that reached each point; cost is not in this data and "worth" is the team's call. Never an amount of money.
- **"Which source has the best candidates?"**, "who refers the best people?", "which sourcer is doing well?": not answered. Sources are described by counts; people and colleagues are not compared. Offer the row, or `/greenhouse:candidate-debrief` for one person's feedback.
- **A source named after a person or an agency**: print the name as recorded, counts only, no comment on them.
- **Req opened inside the window**: say "the req opened d days ago, so this is every application on it."
- **Closed req**: reviewable; say it is closed and when; the window still counts back from today, so when it comes back empty offer "since it opened".
- **Every source under ten applications**: no percentages anywhere; say "too few applications per source for rates; counts only."
- **Confidential req**: add "Confidential job: share only with its hiring team."
