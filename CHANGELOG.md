# Changelog

All notable changes to the Greenhouse plugin. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/).

## [0.2.0] - 2026-11-23

### Added

- An OpenAI plugin manifest (`plugin.json`, Agent Plugins format) and MCP config (`mcp.json`) beside the existing ones, so the same plugin folder uploads to OpenAI's plugin directory. The MCP config uses OAuth with client ID metadata document registration and holds no credentials or headers; `assets/icon.png` is the listing icon and logo. The linter keeps both manifests in step.

## [0.1.0] - 2026-10-16

First release. Greenhouse MCP is in open beta; the plugin runs in any AI assistant that supports plugins and MCP connectors, in the desktop or web app and in a command-line client.

### Added

- `configure`: checks the connection, matches the user's Greenhouse account (`whoami` when the connector lists it, so nobody is asked for an email; otherwise the lowercased login email, with a bounded alias fallback), reports which skills the session's MCP access unlocks (Ready, Partial when only enhancements are missing, or Not yet with the missing scope keys when a core tool is missing) with a filled "Try" prompt per skill, prints the Site Admin note ready to send when scopes are missing, and lands the user in four sentences with a place to start; shown as a page.
- `daily-brief`: a headline for the day, then decisions waiting, scorecards started but not submitted, quiet candidates, new applicants since the last working day and a pipeline snapshot with a status word and the review backlog per req; interviews, offers with their start dates, and the hiring manager per req when those scopes are enabled. Shown as a page filtered by req, with a short reply naming up to three things that need the user; reminder nudges go to interviewers through a connected chat or email tool, one per yes.
- `interview-week`: the next 7 days of interviews by day and time with candidate, req, interview and status, each panel and its calendar replies, what still needs scheduling, and past interviews from the last 30 days still waiting on feedback by interviewer with a nudge for each, sent through a connected chat or email tool only on a yes; no ratings or scorecard text. Shown as a page. On the default scopes it shows scorecards started but not submitted and names the missing scope in its footnote; the calendar, what still needs scheduling and interviews awaiting feedback need `harvest:interviews:list`, panels and their replies `harvest:interviewers:list`, interview names `harvest:job_interviews:list`.
- `candidate-status`: one sentence that answers the question (where is, still active, have we talked before), then every application for one candidate with stage k of n, the recorded outcome and reason, days since recorded activity, scorecards in and owed, what is next and whom to ask; next interview, offer state and last logged email when enabled; a quick mode for one-line questions; a page on request.
- `candidate-debrief`: whether the panel's input is in, ratings and quoted takeaways as given (content read only for complete scorecards, private notes only on request), where the panel disagrees and agrees, up to six questions for the room, current and next stage; no recommendation; a page on request, for the hiring team only and never a candidate, with private notes left off; no page for an opted-out candidate or while the user's own scorecard on the application is still a draft.
- `pipeline-review`: one req's status and risks by rule, funnel with how far people got, bottleneck, late-stage roster with scorecard tallies (withheld for candidates who opted out of AI review when that scope is enabled), who ended the rejections in the last 30 days, questions for the sync split between the hiring manager and the recruiter, and a hiring-manager message under 120 words that is safe to share, sent to one person through a connected chat or email tool only on a yes. Shown as a page.
- `source-review`: for one req or the user's open reqs over a stated window (90 days by default), applications per source, active now, reached the first interview and the final stage, hired, ended and who ended it, referrals as their own line, sources with nobody past review, and questions for a sourcing sync. It counts sources, never people, and names no candidate or referrer. Shown as a page. On the default scopes it gives the totals and the referrer line and says source names are not visible; per-source rows need `harvest:sources:list`, and "Reached" from stage history needs `harvest:application_stages:list`.
- `scorecard-draft`: the user's own interview notes turned into a draft scorecard for the matching interview kit, with a "checked just now" duplicate line on the card; paste-ready text when the scorecard scopes are missing.
- `brand`: Greenhouse's visual style (the palette from Greenhouse's visual guidelines with light and dark values, Merriweather and Nunito Sans as stand-ins for the brand faces, the plugin's own chart series order and diagram rules, status chips, document, deck and spreadsheet rules) applied to anything shown beyond prose that no skill's page folder builds: markdown tables, SVG and Mermaid diagrams, charts, HTML pages, documents, decks and spreadsheets. It styles only and reads nothing from Greenhouse.
- Pages: seven data skills carry a `page/` folder (`PAGE.md`, `page.html`, `build_page.py`, `example.json`). `configure`, `daily-brief`, `interview-week`, `pipeline-review` and `source-review` open a page by default; `candidate-debrief` and `candidate-status` build one when asked; "in chat" skips it. The assistant passes the run's figures to the bundled Python builder on standard input in one shell call; the builder checks them against the page schema, accepts only `https://app.greenhouse.io/` links, refuses common formats of email addresses, phone numbers and amounts of money, fills the fixed template and writes the page under the name each `PAGE.md` gives (`greenhouse-daily-brief-<date>.html`, `greenhouse-setup.html`, `greenhouse-pipeline-<req>.html` and so on) to the app's outputs folder; no data file is written. Where Python cannot run, or the build fails twice, the assistant writes a plain still page itself from the "Without Python" frame in `PAGE.md` (no script, Greenhouse links only); where the app can show neither a file nor an artifact, the answer arrives in chat. A page filters and sorts, opens rows, and copies messages and Next prompts; opening the builder's page requests two typefaces from Google Fonts.
- Every answer: headline and scope line ("that you can see", "as of"), a line stating every threshold with its reason ("Tell me different numbers and I'll redo it.") on the page or when asked, one footnote for anything the MCP access hides, and "Next:" prompts filled with the run's real names. A short reply beside a page is what its `PAGE.md` defines, under about 120 words in a colleague's voice; for the desk-level skills (`daily-brief`, `interview-week`) that is the headline, up to three linked bullets for what needs the user, an "Also:" counts line, where the rest is, one plain sentence for anything hidden, a short scope line and Next; the threshold line and the exact footnote live on the page.
- Shared behaviour in every data skill: access failures reported with the Greenhouse MCP server's exact wording, one footnote naming the sections a hidden tool left out and their scope keys, and a Needs table saying what the skill does when a core tool is missing; write cards that say who is notified and how to undo, with a "yes" that answers only the card on screen; messages only through a connected chat or email tool; an AI opt-out check that cannot run reads "could not be checked"; the year in dates outside this one; and the hand-off to `brand` for any other visual.
- Default access: every data skill, `interview-week` and `source-review` included, runs on the default MCP Access scopes and footnotes the scope keys for what it could not show; no skill requires a non-default scope, and `configure` rates a skill Partial when only enhancements are missing. `whoami` is a Greenhouse MCP server tool, not a Harvest scope; where the connector lists it the skills recognise the signed-in user, and without it they fall back to the login email.
- Files: the skills are written to save nothing to memory or schedules on their own. The page is the only file they write, into the app's outputs folder or, in a command-line client, the session's scratch or temporary directory, never the user's project, and it stays until the user deletes it; no data file is written. `configure` prints a profile line the user can keep.
- Install: plugin `greenhouse` from marketplace `greenhouse-skills`, with the Greenhouse MCP server at `https://mcp.greenhouse.io/mcp` and links to documentation, support, the Greenhouse AI Addendum and terms.
- Docs: plugin README (with what the plugin runs, sends and fetches), SETUP and DATA_HANDLING; repo README, CONTRIBUTING and SECURITY; `docs/` with failure states, a data-model reference, one rendered sample per skill on a fictional organization and, for contributors, the shared-rules source and skill conventions.
- License: the plugin ships under the Greenhouse Skills License (proprietary): Greenhouse customer use only; see LICENSE and NOTICE.

### Writes

The complete list of writes in this release. The skills are written to preview each one and make it only after an explicit "yes" in the user's next message, one per confirmation, and to read Greenhouse writes back afterwards.

- `add_candidate_note` in `candidate-debrief`.
- `move_application` in `candidate-debrief`, with the destination stage's rules (which can email the candidate or the team and send forms, tests or scheduling requests) named on the card and the undo stated.
- `create_scorecard` with `status: draft` in `scorecard-draft`, for the user's own interview only.
- A message through the user's own connected chat or email tool, outside Greenhouse: an interviewer nudge in `daily-brief` (step 8) and `interview-week` (step 9), the hiring-manager message in `pipeline-review` (step 5). Each skill gates it in its own step: the whole message and its one named recipient are shown, the draft ends with a line asking for a yes (`Reply yes to send this to <interviewer name>.` for a nudge, `Reply "yes" to send.` for the hiring-manager message), one message goes out per explicit yes, to that person and never a channel or group; a nudge carries no ratings, notes or contact details, and the hiring-manager message no ratings, scorecard text, contact details or compensation. Asked to post somewhere shared, `daily-brief` and `interview-week` send a counts-only snapshot (`daily-brief`: counts only, no names, confidential reqs counted and not named; `interview-week`: counts and times only, no candidate names) to the destination shown, one send on an explicit yes.
