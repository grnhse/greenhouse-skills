# Skill conventions

Every skill in `greenhouse/skills/<name>/SKILL.md` follows this shape. `lint_skills.py` enforces the measurable parts. Eight are data skills that read Greenhouse, seven of them with a `page/` folder (see Pages); one, `brand`, is a style skill with its own shorter shape (see the end of this page).

## Frontmatter

```yaml
---
name: candidate-status                      # equals the directory name, kebab-case
description: "Locate a candidate ... Use when someone says \"where is Priya\", ... ; the panel's feedback or a stage move: candidate-debrief. It never summarizes interview feedback."
license: "© 2026 Greenhouse Software, Inc. Greenhouse customer use only. See LICENSE."
metadata:
  core: [search_applications, list_applications, list_candidates, search_candidates, list_jobs, list_job_stages, list_scorecards, list_rejection_reasons, list_users]
  enhancement: [whoami, list_interviews, list_offers, list_application_stages, list_notes]
  write: []                                 # only add_candidate_note, move_application, create_scorecard
---
```

- Only these keys: `name`, `description`, `allowed-tools`, `argument-hint`, `compatibility`, `disable-model-invocation`, `license`, `metadata`, `model`. `license` carries the notice above, word for word, in every skill and in `plugin.json`.
- `metadata` lists every Greenhouse tool the body mentions, by role: `core`, `enhancement`, `write` (the linter also accepts `required`, which no shipped skill uses; see Needs). The linter cross-checks the body against it and against the tool catalog. `whoami` is listed under `enhancement` in every data skill: it is a tool of the Greenhouse MCP server, not a Harvest scope, and is listed on every connection where the server enables it, so it sits outside the MCP Access ceiling. In `configure`, `core` means the tools it calls and `enhancement` the tools it only inspects for presence, `whoami` excepted: `configure` calls it as the probe and for identity. The style skill carries `kind: style` instead of tool lists.
- `configure` stays model-invocable (no `disable-model-invocation`) so "set me up with Greenhouse" keeps working; typing `/` then `greenhouse:configure` in chat also reaches it.

## Description formula

The description is the only thing the assistant reads before deciding to use a skill, so it carries the deliverable, the words a recruiter would type, and the routing to siblings. Quote the phrases recruiters type, so the skill fires when it should and hands adjacent requests to its siblings.

`<Verb> <deliverable> from Greenhouse <objects>[, plus <capability> when connected]. Use when someone says "<phrase>", "<phrase>", "<phrase>" or asks <intent>; <adjacent case>: <sibling-skill>; <adjacent case>: <sibling-skill>. <The one thing it never does, when a user might expect it>.`

- Aim for 300 to 900 characters (`source-review` sits at 940), one line, in double quotes. The hard limit is 1024 (a command-line client truncates beyond it); the linter allows 120 to 1024.
- Action-first, third person, no angle brackets. The sentence that starts with `Use ` is required (the linter checks for it).
- Quote four to eight trigger phrases, taken from the words recruiters use ("what needs me today", "where is Priya", "prep my sync with Dana").
- Route every adjacent request to the sibling that owns it, by skill name without the `/greenhouse:` prefix.
- Name the boundary a user might expect the skill to cross: `candidate-status` never summarizes feedback; `candidate-debrief` never recommends; `pipeline-review` writes nothing in Greenhouse; `interview-week` schedules nothing; `source-review` counts sources, never people; `brand` reads nothing from Greenhouse.

## Body order (data skills)

1. The shared rules block between `<!-- greenhouse-rules v8 -->` and `<!-- /greenhouse-rules -->`, injected from `docs/shared-rules.md` (never edit it in place; edit the source and run `inject_shared_rules.py`).
2. `# <Title>` and a one-line pipeline with the call budget: an arrow pipeline where the flow needs stating, otherwise the `Budget:` sentence alone, e.g. `Budget: 6-8 calls on the default tools, 8-14 with both enhancements; paging adds at most two calls per application list. No Greenhouse writes.`
3. `## Needs`: a table `Tool | Role | Without it` of every tool with its role (core, enhancement, write; `whoami`'s reads "optional: who is asking, with no email question"; `configure`: "the probe and who the user is, with no email question"). "Without it" names the nearest true substitute in at most twelve words ("days in stage" → "no activity recorded for n days"; "hiring team" → "recruiter and coordinator on the applications"), never "omitted" alone. Core tools are the ones present under the default MCP Access ceiling; a skill must be useful with core tools alone. Every other tool is an enhancement that degrades per rule 1, including the ones a skill is named for: `interview-week` without `list_interviews` shows scorecards started but not submitted ("interview times: not visible"), `source-review` without `list_sources` gives the totals and the referrer line ("n applications across k recorded sources, names not visible"), and `configure` rates both Partial. No shipped skill declares a `required` tool (one outside the default ceiling that the skill cannot answer without); the linter still accepts the role, and adding one needs maintainer approval in the pull request. Enhancement rows point to the section below for the call.
4. `## Steps`: the default-tools path only, numbered, with the exact call shapes (`list_applications(job_ids: JOBS, status: "active", prospect: false, per_page: 500, fields: [...])`), which steps run in one parallel batch, and where the enhancement reads join a batch. Gates that depend on an enhancement tool (the AI opt-out check) stay in Steps because they change the flow; everything additive moves to the next section.
5. `## With more tools switched on`: one table, `If this is listed | Read (when, and in which batch) | What changes`, one row per enhancement and write tool except `whoami`, whose call lives in the identity step, in the order the Needs table lists them (`interview-week` puts `list_job_interviews` before `list_interviewers`). The row carries the exact call shape, the section or column it adds, and the wording that replaces it when the tool is absent. Writes get a row that points to the preview steps. `configure` calls no enhancement tool but `whoami`; its capability map stands in for this table and says so in one sentence.
6. `## Output`: in a skill with a page folder, it opens with the `Page:` line (see Pages) and the long template lives in `page/PAGE.md` as "Output, full version", beside the short reply that replaces it next to a page; otherwise the markdown template. Line one is a headline sentence that answers the question with the biggest number in it (the rule that picks it is in Steps); line two is the scope line, ending with "that you can see" and "as of <date and time>". Then the sections, each with its empty-state sentence; a "How this was ranked" (or read, judged, counted) line stating every threshold and definition used, ending "Tell me different numbers and I'll redo it."; the rules block footnote for anything not visible; then `Next:` with two or three prompts filled with the real names and reqs from this run, each leading to a named sibling skill. A write card ends the message (`Reply "yes" to proceed.` is its last sentence); Next follows the read-back or the paste-ready block, never the card.
7. `## Edge cases`: at most seven bolded one-liners (only `source-review` uses all seven; the rest carry six or fewer) for the odd-but-real situations the steps do not cover (two people with the same name, a private candidate, a template job, a weekend, "asked to act on a row", "asked what you would do").
8. `## Next`: the rule for choosing and filling the Next prompts, by skill name, and what to offer when a tool is missing (`/greenhouse:configure`).

## Hard rules

- Bare tool names only. Never `mcp__...`.
- Tools present under the default ceiling: `list_applications`, `search_applications`, `list_candidates`, `search_candidates`, `list_job_stages`, `list_jobs`, `search_jobs`, `get_job`, `list_rejection_reasons`, `list_scorecards`, `list_users`: eleven Harvest tools behind the seven default scopes. Everything else is an enhancement and degrades per the rules block. `whoami` is outside the ceiling altogether: an unscoped server tool, listed whenever the server enables it, so no footnote ever names a scope for it.
- `needs_decision`, `rejected_at` and `days_in_stage` are response fields, not filters; filter client-side. `list_applications` does accept `last_activity_at`, `created_at` and `updated_at` ranges (`gte`, `lte`, `gt`, `lt`). Rejections in a window: filter on `updated_at` and keep the rows whose `rejected_at` falls in the window.
- Never send an empty id list. When an earlier step found nothing, skip every call that would filter on it and go to the empty state.
- `search_applications` and `search_candidates` default to open reqs; pass `job_status: "all"` for anything about the past. `search_jobs` defaults to every status; pass `status: "open"` for open reqs.
- `move_application` stage ids come from `list_job_stages`, never `application.stage_id`.
- Writes: preview with what changes, on whose record, whom Greenhouse may notify (a move runs the destination stage's rules, which can email the candidate or the team and send forms, tests or scheduling requests; never tasks) and how to undo it; explicit yes to that preview; one record; read back. Never `confirm`.
- Identity, in the order the rules block fixes: a "Greenhouse profile:" line or a Greenhouse user id the user stated, used as given; `whoami` when it is listed (no arguments; it returns the signed-in user), so nobody is asked for an email; else `list_users(primary_email:)` on the login email the user gave, in the conversation or in the instructions they wrote for the assistant, asked for once when they haven't. A skill never describes itself as reading the assistant's memory, history or files.
- Wording that the rules block fixes: "no activity recorded for N days" (never "nothing has happened", never "days in stage" unless from `days_in_stage`); `needs_decision` means a decision is waiting on the application, never "waiting on you" or "on the hiring manager"; "that you can see", never "in the company"; a blank field is a finding and sorts first; "not checked" when a read was not made, "not visible" when the tool is hidden, "none that you can see" when a list came back empty.
- Thresholds are inclusive, stated with one line of why, and the user's own numbers win. One quiet number per skill: `daily-brief` uses 14 days (7 in the first stage, from the day they applied) because it spans a whole desk; `pipeline-review` uses 7 days because one req's late stages move faster; `candidate-status` flags 14. Windows: `daily-brief` counts scorecards from the last 14 days; `interview-week` looks 7 days ahead and 30 days back for interviews awaiting feedback, and for scorecards started but not submitted on the default tools; `pipeline-review` reads rejections from the last 30 days; `source-review` reads applications created in the last 90 days by default, calls those from the last 14 days fresh because they have had little time to move, and asks about a source only at five or more applications.
- Ask for everything missing in one message, never one question per turn; a quick one-line ask gets a one-line answer and skips the reads it does not need.
- Resolve recipe, shared by the resolve steps: "my reqs" → `search_jobs(user_id: ME, user_role: "recruiter" | "coordinator", status: "open", per_page: 100)`; a req by title → `search_jobs(search:, status: "open")`, re-issued with `status: "all"` for the past; a job id → `get_job(job_id:)` (`[]` is not found or not visible), or the `search_jobs` row whose `id` matches when a name came with it; a person → `search_applications(search:, job_status: "all")`; more than 50 reqs → say how many and ask which department or reqs first. One exact match carries on; none or several are shown with one distinguishing detail and asked about; two people with the same name are never chosen between. If a step yields no ids the answer is "none": stop there.
- A Next prompt names a person or a req, never a direction ("Debrief Priya Shah on Senior Backend Engineer", never "Advance Priya").
- Under 200 lines and 32 KiB (32,768 bytes, the linter's limit; `configure` sits within 200 bytes of it), including the rules block. A skill with a page folder moves its long templates to `page/PAGE.md`, which every surface can read; a skill without one cuts them. Never a `references/` folder.
- No scripts except the shared page builder, `page/build_page.py`. No `!` dynamic context and no path variables: the page run line names the skill's folder in words, `"<this skill's folder>/page/build_page.py"`.
- A page where the skill's `Page:` line says, markdown in the chat everywhere else, and never a question about which. Any other chart, diagram, document or deck is made only when the user asks, and then `brand` decides how it looks while the data skill still owns what is shown, hidden, counted and confirmed.

## Pages

`configure`, `daily-brief`, `interview-week`, `pipeline-review` and `source-review` open a page by default; `candidate-debrief` and `candidate-status` build one only when the user asks; `scorecard-draft` and `brand` have no page folder. The user saying "in chat" skips the page.

- **Folder.** `page/` holds exactly `PAGE.md`, `page.html`, `build_page.py` and `example.json`. `page.html` and `build_page.py` are byte-identical in every skill: edit the `daily-brief` copy and copy it out (see CONTRIBUTING). Never edit `page.html` per skill, and the assistant never writes or patches the builder's HTML; the one page it writes itself is the "Without Python" fallback below.
- **The `Page:` line.** The skill's Output opens with it. By default: "Page: read `page/PAGE.md` in this skill's folder before rendering and follow it. It holds the page, the short reply and the full Output these steps refer to." (`configure` reads it "before the final answer of a completed run".) On request: "Page: read `page/PAGE.md` in this skill's folder before rendering and follow it. It holds the chat reply, the page (built only when asked) and the Output these steps refer to." PAGE.md is always read; only the page waits for the ask. Every `Page:` line ends with the fallback (below): what to answer "If it cannot be read".
- **PAGE.md shape.** `# <Skill>: how to answer`, then which shape fits. Default-page skills: a page and a short reply; the short reply only; one section or the full Output in chat, only when asked; then `## Short reply`; `## Data file` (the file name and the keys of the short form the builder expands); `## Build`; `## Without Python`; `## Next prompts`; `## Output, full version` (the long template the steps refer to). `configure` adds `## Rolling this out (Site Admins)` before Data file. On-request skills (`candidate-debrief`, `candidate-status`): the chat reply always, a page as well only when asked; then `## Chat reply` (`## Chat reply, FULL mode` in candidate-status); `## Panels` (file name, title, `meta`, `tiles`, one row per panel); `## Build`; `## Without Python`; `## Next prompts`; `## Data file` (the page schema the builder takes as is); `## Output, full version`. A filled `example.json` on a fictional organization must build.
- **The run line**, in every PAGE.md's Build step: one shell call, the page data on standard input as a heredoc:

  ```
  python3 "<this skill's folder>/page/build_page.py" --out "<outputs folder>/<the file name this file gives>" <<'GH_PAGE_DATA'
  { ...the data this file describes, as JSON... }
  GH_PAGE_DATA
  ```

  The skill's folder is named in words, with no variable. `<outputs folder>` is where the app keeps files it shows the user (its outputs or artifacts directory); in a terminal app, the session's scratch or temporary directory, never the user's project. PAGE.md gives the file name and it goes on `--out`: `greenhouse-daily-brief-<yyyy-mm-dd>.html`, `greenhouse-setup.html`, `greenhouse-interviews-<yyyy-mm-dd of the window's first day>.html`, `greenhouse-pipeline-<req name in lower-case words joined by hyphens>.html`, `greenhouse-sources-<req name slug>.html` (or `greenhouse-sources-my-reqs-<yyyy-mm-dd>.html` across reqs), and for the two on-request skills `greenhouse-debrief-<candidate name slug>.html` and `greenhouse-status-<candidate name slug>.html`. No data file is written, so there is nothing to delete; the builder's `--data <file>` option exists but no skill uses it. The short reply goes out as text before the build, and the user never hears how the page was made: no mention of Python, scripts, files or folders.
- **Builder.** It accepts only `https://app.greenhouse.io/` links (any path on that host), refuses common formats of email addresses, phone numbers and amounts of money in any string, and embeds the data as escaped JSON in the fixed template; nothing from the data is executed and nothing is fetched. On success it prints the page's path; on problems it prints them and exits 1. The assistant fixes the data and runs it again, twice at most, then shows the page with the app's own file or artifact tool, saying only "The page is up." or what it could not build.
- **Without Python.** If Python cannot run, or the build still fails after two fixes, the assistant writes the page itself as PAGE.md's "Without Python" section says: one self-contained still HTML document from the frame and style block PAGE.md gives, copied exactly with only the capitalised words and the rows changed, as an artifact when the app has them and otherwise as a file with the same name. The builder is not there to check it, so the assistant does: no script, image, font or other outside resource (only the builder's page loads the two Google Fonts faces); links only to `https://app.greenhouse.io/`; `&`, `<` and `>` escaped in every value; never an email address, a phone number or an amount of money; at most 10 rows per table, then "and N more". It is shown with "The page is up." and never called a simpler page. This is the one exception to the rules block's "Never hand-write a page". If the app can show neither a file nor an artifact, the short reply goes on its own with one plain line: "I couldn't open a page here, so it's all in chat: ask for any section."
- **Short reply** beside a page, as PAGE.md defines it and in its order, which replaces the rules block's "headline, then scope line": a greeting with the user's first name by their local time and the headline sentence (desk-level skills; `pipeline-review` and `source-review` put the first name in front of the headline instead, `configure` opens with its landing sentences); up to three linked bullets, most urgent first, each a person or a req with the reason in a few words (`source-review`: a source and its numbers, never a person); an "Also:" line of counts, leaving out zeros; where the rest is ("It's all on the page: ..."); a one-line offer where the skill has one (reminders, the hiring-manager message; `source-review` gives the first question for the sync instead); one plain sentence only if something was hidden or declined, in the user's words, with the one thing that would fix it; the scope line, short ("Across your <N> open reqs, counting what you can see in Greenhouse, as of <Wed 14 Oct, 09:00 EDT>."); Next as two prompts in text, never through a question tool. Under about 120 words; no headings, tables, tool or rule names. The threshold line, the long footnotes and the per-section lead lines are not in the short reply: they are on the page (`judged`, `notes`) and come to chat when asked. The on-request skills send their chat reply and, with a page, say where it is ("The evidence brief is on the page.", "The applications and the timeline are on the page.").
- **Fallback** when PAGE.md itself cannot be read, from the SKILL.md `Page:` line. Default-page skills: with artifacts, one titled document artifact holding every section the steps computed (a heading and a table or list per section, links kept, the thresholds line last) and a chat reply with the headline, up to three linked bullets for what needs the user, "The rest is in the document." and Next; without artifacts, the headline, the scope line, up to three linked rows that need the user, rule 1 and rule 2 lines and Next, a table only when asked (`configure`: the landing, the scope line, the profile line and the chooser; `source-review`: the three rows with the most applications and the referrer line). On-request skills name their own: `candidate-status` the headline, the scope line, one line per application with status, stage and what is next, and Next; `candidate-debrief` line 1 with the tally, the header line, one row per interviewer with rating and one quote, who still owes a scorecard, the hiring-team-only line, the decision line and Next.

## Call budgets

State the budget in the pipeline line. Targets on the default tools, then with every enhancement, as each skill's `Budget:` line gives them: `configure` 5 Greenhouse calls (6 with the alias fallback); `candidate-status` 4-5 in QUICK mode, 7-8 in FULL, up to 11 with the duplicate sweep, 11-12 with every enhancement; `candidate-debrief` 7-8 reads (two-phase scorecard read), 11 with every enhancement, 15 with a note and a stage move, 16 when the move card re-reads the application first; `daily-brief` 9, 13 with every enhancement, hard cap 16; `pipeline-review` 8-11, 15-18 with every enhancement, paging adding at most one call per list; `interview-week` 7 on the default tools, where the calendar itself is not visible, 13-15 with every enhancement, hard cap 18; `source-review` 6-8, 8-14 with both enhancements, paging adding at most two calls per application list; `scorecard-draft` 3 reads in paste-ready mode, 6-8 reads to the preview (7 when several kits need naming, 8 when the user's id is not in the profile line), then 1 write and 1 read-back. A page build is one script run, not a Greenhouse call, and is outside the budget. Batch ids up to 50, use `fields`, `per_page` 500 for data you aggregate and 100 or less for data you print, at most three pages per list. The reads in "With more tools switched on" join an existing batch; they never add a turn.

## Style skill

`brand` is the one style skill. Its frontmatter carries `metadata: kind: style` and no tool lists; the linter and the injector then expect no rules block and fail if it names a Greenhouse tool. Same description formula and size limits as the data skills. Body order: title and one-paragraph scope, When this applies, Palette, Type, Markdown tables, Pages and artifacts, Charts, Diagrams, Documents, decks and spreadsheets, Never, Edge cases (at most six), Next (hand back to the data skill). Every colour is a named swatch from Greenhouse's public visual guidelines; every contrast claim is computed, not eyeballed; the skill restates the people-and-data rules a visual depends on (ratings never totalled or colour-coded, no verdict colours on a person, no contact details or scorecard text on anything shared) rather than carrying the full block. Provenance on anything it styles reads "the Greenhouse plugin" and nothing else: the plugin ships no logo, so Greenhouse appears in text only, and nothing implies a partnership with or an endorsement by the maker of any AI tool.
